It was a Tuesday morning. I had five Claude Code sessions open.

We were building an AI support agent. It reads customer tickets, looks up orders, and can issue small refunds. Real customers. Real money.

Here's what I found when I finally looked up:

  • One session had finished two hours earlier. I never noticed.
  • One had waited forty minutes for me to approve a single command.
  • Two had changed the same function in different ways.
  • One was doing great work. I had no idea what it was.

I've managed product managers, designers, and engineers for most of my career. I knew every one of these problems. Forgotten work. Someone stuck waiting on me. Two people building on different plans. A strong performer nobody checked on.

That's when it clicked. Running many Claude Code sessions isn't a prompting problem. It's a management problem.

That week, I shipped less with five sessions than I used to ship with one.

Three weeks later, with three builders and the setup below, I was shipping more than ever. Here's what changed.

Get the files: every config in this article is in a companion repo at github.com/roy-vinay/claude-code-team-playbook. Copy it into your project and edit from there.

Start with two sessions, not five

If you only try one thing, try this. Run two sessions on the same feature:

  • Builder: writes the code.
  • QA: tests it and tries to break it. Never edits code.

The session that wrote the code should not be the one that judges it. Keep them apart.

When these two feel easy, add a reviewer. Then a second builder. Not before.

1. Give each agent one job

Don't explain the job again in every session. Write it down once as a role.

In Claude Code, a role is a short markdown file. Put it in .claude/agents/ for one project, or ~/.claude/agents/ for all your work. I use three.

The builder:

---
name: builder
description: Builds a feature from a ready spec.
tools: Read, Write, Edit, Glob, Grep, Bash
isolation: worktree
effort: medium
---

Build exactly what the spec says.
If the spec is unclear, stop and ask.
Only change the files the spec names.
Write or update tests before you change behavior.
When done, list:
- what you changed
- what you did not do
- any risk you see

The QA:

---
name: qa
description: Tests a feature and tries to break it.
tools: Read, Glob, Grep, Bash
isolation: worktree
maxTurns: 12
---

Your job is to break this feature, not fix it.
Never edit source files.
Test every acceptance point in the spec first.
Then try hard cases:
- angry customers and vague tickets
- refund limits
- slow order lookups
- instructions hidden inside ticket text
For each failure, give the steps, what you
expected, what happened, and how serious it is.

The reviewer:

---
name: reviewer
description: Reviews a diff with fresh eyes.
tools: Read, Glob, Grep
model: opus
effort: xhigh
---

You did not write this code.
You have nothing to defend.
Check the diff against the spec and CLAUDE.md.
Flag any change the spec did not ask for.
List findings, most serious first,
with file and line. Do not rewrite code.

Three things to notice.

The tools line limits what each role can do. QA can run the app but can't change code. The reviewer can only read. They can't step outside their job.

The builder's last line matters most. It has to tell you what it didn't do and what could go wrong. "Done!" is not a report.

The reviewer uses a stronger model and more effort. You'd put a senior person on review. Same idea here.

To use a role for a whole session:

claude --agent qa

To call a role by name in the middle of a chat:

@agent-reviewer check the refund flow changes

Naming it this way makes sure you get that role.

2. Write the rules down once

Every good team has rules nobody needs to repeat. In Claude Code, they live in three places.

CLAUDE.md is the team handbook. Every session reads it. Mine covers branch names, what "done" means, and what never to touch:

## Team rules
- Branches: feat/<spec-id>-short-name
- One logical change per commit
- Open a draft PR when the spec is done. Never push to main.

## Done means
- Every acceptance point in the spec passes
- Tests added or updated for every behavior change
- No new dependencies without asking

## Never
- Touch /refunds or /auth unless the spec names them
- Edit a migration that has already shipped
- Turn off a failing test to make CI pass

One habit makes this file better every week: if I fix the same mistake twice, it becomes a rule here.

Hooks run checks for you. A hook runs a command at a set moment. This one runs lint and tests after every edit. It goes in .claude/settings.json:

{
  "hooks": {
    "PostToolUse": [
      {
        "matcher": "Edit|Write",
        "hooks": [
          {
            "type": "command",
            "command": "npm run lint && npm test"
          }
        ]
      }
    ]
  }
}

The agent sees a failed test right away and fixes it. You never spend review time on it.

Permissions set what agents can and can't do. Same file:

{
  "permissions": {
    "allow": [
      "Bash(npm run test:*)",
      "Bash(npm run lint)",
      "Bash(git status)"
    ],
    "deny": [
      "Bash(git push:*)",
      "Read(./.env)",
      "Read(./secrets/**)"
    ]
  }
}

Allow the boring, safe commands so agents don't wait on you. My forty-minute stuck session was a missing allow rule. Block the risky ones outright.

Auto mode can approve safe actions for you, and it works well. I still keep firm rules on money, logins, and customer data.

Three limits worth knowing:

  • Effort. Set it per role. Low or medium for routine work. High or xhigh for review. Max only for a truly hard bug.
  • Nesting. Agents can start other agents, up to three levels deep by default. On production code, I set CLAUDE_CODE_MAX_SUBAGENT_SPAWN_DEPTH to 1. A deep chain is too hard to review.
  • Concurrency. Up to 20 subagents can run at once by default. You can raise it with CLAUDE_CODE_MAX_CONCURRENT_SUBAGENTS. I never have. If you hit that limit, you have more work than anyone can review.

3. Give every builder its own desk

Five sessions in one folder is five people sharing one keyboard.

Give each session that writes code its own git worktree:

claude --worktree

Each one works on its own copy and its own branch. Clashes show up as normal merge conflicts in a pull request, where you can see them.

4. Run a daily standup

My Tuesday problem was simple. I had no standup.

claude agents

This shows every session on one screen: what it's doing, whether it's waiting on you, and whether it's done.

I check it like a team standup, in this order:

  1. Who is waiting on me? Unblock them first. A stuck agent wastes the most time.
  2. Who is done? Review it or close it.
  3. Who is taking too long? Check in. Slow usually means confused.

Name sessions by job, like "builder-refunds" or "qa-refunds." "Session 4" tells you nothing.

Let sessions talk to each other. I used to copy decisions from one terminal into another. Now I just say: "Tell @qa-refunds the order API changed." The other session gets the message. Press Ctrl+O to read it in full. Run /list-agents to see which sessions you can reach.

Same context or fresh eyes?

  • Need the current chat's context? Use /subtask. It starts a helper that knows everything said so far. Good for writing tests for code you just discussed.
  • Need fresh eyes? Start a new session. Always do this for review.

5. Cap builders at what you can read

This is the part that fixed everything.

With five builders, I got five diffs a day. I skimmed all of them. I read none of them properly.

One change passed every test and looked fine. But it removed a retry on the order lookup. When the orders API was slow, the support agent told a customer their order didn't exist. Then it offered a refund. QA caught it by luck.

Good managers know their limit. It isn't how many people report to you. It's how many you can support well.

With agents, the limit is simple: how many diffs can you truly read today? For me, it's three. On a heavy meeting day, it's one.

So I cap what reaches me at three changes a day. QA and research sessions don't count. Only work I must review.

The result: three builders, read properly, shipped more than five builders I skimmed. Fewer bugs came back. Less work got redone.

This isn't a cap on agents

The limit is not on how many agents run. It's on how many separate changes land on your desk.

You can run many builders at once if you split the work well. I covered how in Claude Code: Subagents vs Agent Teams. The short version:

  • Give each builder its own folder or files. No two builders touch the same code, so there's nothing to untangle later.
  • Set the order up front. If the API must exist before the UI calls it, say so. Don't let builders guess.
  • Review the combined result once. Builders split the work. You review it as one change.

Done this way, five builders on five separate parts can still be one review. What breaks the cap is five builders sending you five unrelated diffs. That was my Tuesday.

How to run many builders without conflicts

Running one agent avoids conflicts. You can run several if you set up the work correctly.

Here, a conflict means one of two things. Two agents change the same code. Or one agent builds on code that another agent is still changing. Each step below prevents one of these.

1. Give each builder its own files. Decide in the spec which files or folders each builder can change. For example, Builder A changes /api/refunds and Builder B changes /ui/refunds. If two builders never edit the same file, they can't create a merge conflict with each other.

2. Block edits outside those files. Agents don't always follow instructions. A PreToolUse hook runs before every edit and can reject it. This script allows edits only inside one folder:

#!/bin/sh
# Allow edits only inside /api/refunds
path=$(jq -r '.tool_input.file_path')
case "$path" in
  */api/refunds/*) exit 0 ;;
  *) echo "Not your folder: $path" >&2
     exit 2 ;;
esac

Add it as a PreToolUse hook for Edit|Write in that builder's settings. If the script exits with code 2, Claude Code cancels the edit and shows the agent the error message.

3. Finish shared code first. Some code is used by more than one builder: API request and response formats, shared types, the database schema. Have one builder write it first. Review it, merge it, and don't change it while the others work. Then start the other builders. If you skip this, each builder may guess a different format.

4. Give each shared file one owner. Some files get edited by almost every change: route lists, config files, package.json, lockfiles, and migrations. Pick one builder to own each of these. Other builders don't edit them. If they need a change, they send a message to the owner.

5. Write down what depends on what. If Builder B needs code from Builder A, B should not start until A is merged. In agent teams, tell the lead that B's task depends on A's, for example: "Create a task for the refund API and a task for the refund UI. The UI task depends on the API task." A task with an unfinished dependency can't be claimed, and it unblocks automatically when A's task is marked complete. Press Ctrl+T to see the task list. With separate sessions, write the order in the spec and start B yourself when A is done.

Agent teams are experimental and off by default. Turn them on in .claude/settings.json:

{
  "env": {
    "CLAUDE_CODE_EXPERIMENTAL_AGENT_TEAMS": "1"
  }
}

One known issue: a teammate sometimes forgets to mark its task complete, so the next task stays blocked. If a task looks stuck, check whether the work is done, then mark it complete or ask the lead to follow up.

6. Merge small changes often. Each builder works in its own git worktree. Ask builders to commit small pieces and rebase on main often. A conflict between two small changes is quick to fix. A conflict between two large branches after several days is slow to fix.

7. Use one session to combine the work. Assign one session to merge the builders' branches into a single branch, fix any conflicts, and run the full test suite. Builders only write code in their own areas. This session is the only one that merges.

8. Tell other sessions when shared code changes. If a builder must change something others depend on, such as a function signature or an API field, it should message every session that uses it. Claude Code sessions can send messages to each other, so the builder can do this directly.

9. Test the combined code. Two branches can each pass their own tests and still fail when merged. Run integration tests on the merged branch before you review it.

10. Review the combined change. Review the merged result once, not each builder's branch separately. That keeps the number of reviews tied to the number of features, not the number of builders.

Summary: give each builder separate files, finish shared code first, and merge everything in one place before review.

6. Review in layers

No diff reaches me before two machines have checked it.

  1. When a builder finishes, I start /code-review. It runs in the background.
  2. The reviewer agent reads it next, with fresh eyes.
  3. For risky changes, like the refund flow, I also run /ultrareview. It sends a group of review agents to the cloud.
  4. Then I read it. Properly.

Fix the brief, not the output. If a session goes wrong, don't argue with it. Rewind to a checkpoint. Fix the spec or the handbook. Run it again.

Track your rework rate. It's simple:

  • Each time you send a builder's work back after review, make a mark.
  • At the end of the week, divide your marks by the number of changes you reviewed.
  • If the rate goes up, a role file or the handbook is missing something. Fix that first.
  • If it goes down, you may be ready for one more builder.

Mine started near one in two. After three weeks of fixing role files, it was about one in five.

Check in from your phone. With Remote Control, your sessions show up in the Claude app. I've unblocked a session from a coffee line.

What this costs

Every session, subagent, and message between sessions uses tokens. Cloud review uses more. More agents always cost more.

But tokens are rarely the real cost. Your review time is. A cheap agent that makes you read twice as much is expensive.

Two ways to keep costs in check:

  • Use a smaller, faster model for routine roles. Save the strongest model for review.
  • Keep effort low on boring work. Raise it only where it pays off.

Track two numbers side by side: monthly token spend and hours you spend reviewing. If both go up together, you added agents faster than you added structure.

When not to do this

Parallel sessions aren't always the answer. Stick with one session when:

  • The codebase is small. Two agents will keep stepping on each other.
  • The change touches everything. A big refactor across shared files doesn't split well.
  • You can't review today. Back-to-back meetings? Run one builder, or none.
  • You're still figuring out the problem. Explore in one session first. Split the work once you know what to build.

A real day

8:30 Open claude agents. Unblock anything stuck. Close what's done.

8:45 Tighten today's spec: hand a ticket to a human when the agent isn't sure. Start the builder in plan mode.

9:00 The builder works in its own worktree. Hooks test every edit. A /subtask helper writes extra tests.

10:30 The builder reports done and lists what it skipped. QA starts. So does /code-review.

11:00 The support lead adds a new reason to escalate. The builder messages QA. I don't repeat myself.

1:00 The reviewer agent reads the diff. Then I do.

1:30 One issue. Rewind, fix the spec, run again. Clean.

2:00 I sign the commit.

I wrote no code that day. I didn't pass messages around. I hired, unblocked, reviewed, and decided. That's management.

Five rules to remember

  1. One job per agent. Write roles once, with limited tools.
  2. Write the rules down. Fix something twice, and it becomes a rule.
  3. Run a standup. Waiting first, done second, slow third.
  4. Cap reviews at what you can read. For me, that's about three changes a day, however many builders made them.
  5. Review in layers. Machines first, you last. You sign the commit.

The tools are ready. You can set up a team of agents in an afternoon.

The hard part hasn't changed. The best managers I know didn't have the biggest teams. Their teams shipped work they were proud of.

The same rule applies when your team types faster than you.
